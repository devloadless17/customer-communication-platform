# Production Audit — Executive Synthesis

## Verdict
⚠️ YES, with conditions — Across all 18 dimensions this is a genuinely production-grade system for a 1-customer pilot: idempotency, dedup, transactional outbox, monotonicity guards, tenant isolation, and graceful-shutdown discipline are real and consistently applied. But two CONFIRMED defects must be fixed first because they hit in normal pilot operation: inbound customer messages are silently dropped under transient DB pressure while telling Meta 200 (unrecoverable data loss), and the per-user rate-limit guard is a complete no-op due to NestJS guard ordering. Three more CONFIRMED HIGHs (dead send-retry policy, queued-broadcast stranding, deploy-rollback blind spot) are visible-on-first-incident reliability gaps. None are architectural; all are localized, well-scoped fixes.

## Blocking Issues (must fix before deploy)
1. **Inbound webhook swallows transient DB errors → permanent message loss, Meta told 200** — `runOne` logs-and-swallows every per-event error (incl. `P2024`/`P1001`/`P2034`), so the controller's 503-retry path is unreachable and Meta never re-delivers; the failed inbound has no outbox row, no dead-letter, no recovery trace — `apps/api/src/lib/providers/ingest.ts:97-122` (defeats `apps/api/src/webhooks/meta/meta.controller.ts:195-212`).
2. **Per-user `RateLimitGuard` is a dead no-op** — global `APP_GUARD` runs before the route-scoped `SessionGuard`/`ApiKeyGuard` that populate `req.session`/`req.apiKey`, so the key is always `null` and every session-authed request passes unmetered; the `@RateLimit({perMinute:60})` send cap sized against Meta's 80/min hard limit is inert, leaving only a 10×-looser shared 600/min/IP brake — `apps/api/src/common/rate-limit.guard.ts:141-142`, `apps/api/src/common/common.module.ts:21`.
3. **BullMQ send-retry policy is dead for all transient Meta/network failures** — `executeTextSendJob` re-wraps `MetaSendError` into an `HttpException` that `categorizeSendError` always classifies non-recoverable, so a Meta 503 / rate-limit / network blip stops after attempt 1 instead of retrying; the agent sees a red failed bubble on the first Meta hiccup the pilot encounters — `apps/api/src/messages/messages.service.ts:815-828`, `apps/api/src/messages/send-worker.service.ts:242-281`.
4. **`queued` broadcasts are stranded forever after any crash/restart** — every path persists `status:"queued"` then hands off to fire-and-forget `startBroadcast`; the boot reconciler covers only `running`/`paused`/`scheduled`, so a crash/deploy in the create→claim, team-at-cap-defer, retry, or scheduled-fire window leaves a billed customer-facing broadcast silently never sending (and an inline comment falsely claims a safety net) — `apps/api/src/broadcasts/broadcasts.service.ts:328-387`, `apps/api/src/lib/broadcast-runner.ts:1459,1476`.
5. **Auto-rollback is blind to a failed `ship` step** — rollback fires only on `steps.health.outcome == 'failure'`, but a ship-step abort *skips* health (outcome `skipped`), leaving the new (possibly broken) images + already-swapped Caddyfile live with no automated revert — `.github/workflows/deploy.yml:511,734-735`.

> Note: #3, #4, #5 are HIGH and fixable in hours; if deploy timing is tight they can ship same-day with #1/#2 rather than blocking for a week — but all five should land before the pilot sees real traffic.

### Findings

#### [CRITICAL] `ingestEvents` swallows transient DB errors → inbound messages permanently lost, Meta told 200
- **Location:** `apps/api/src/lib/providers/ingest.ts:97-122` (per-event swallow), defeating `apps/api/src/webhooks/meta/meta.controller.ts:195-212` (transient→503 retry path)
- **Problem:** Every event in a batch is run inside `runOne`, whose `try/catch` logs and **swallows all errors** — including `P2024` (Prisma pool timeout), `P1001/P1002/P1008` (connection/op timeouts), and a `runWithSerializableRetry` that exhausted its 2 attempts. Because `ingestInboundMessage`'s `throw err` (line 795) lands in that swallow, `ingestEvents` effectively never throws for message ingest. The controller's `catch` block that classifies `P2024`→`ServiceUnavailableException` (503, "ask Meta to retry") is therefore **unreachable** for inbound messages — the error is eaten one layer below it.
- **Why dangerous:** Meta retries webhooks only on non-2xx. When the DB is under transient pressure (pool exhausted during a traffic burst — exactly the scenario the 8-lane cap + Serializable retries are fighting, and the scenario the controller code explicitly names), the failed inbound is logged and dropped, and the handler returns `{ ok: true, ingested: events.length }` → HTTP 200. #### [MEDIUM] V8 `--max-old-space-size=4096` exceeds the container `mem_limit` (3g api / 2g web) → cgroup OOMKill before GC
- **Location:** `apps/api/Dockerfile:73` (`--max-old-space-size=4096`) vs `docker-compose.yml:430` (`mem_limit: 3g`); `apps/web/Dockerfile:205` (`--max-old-space-size=4096`) vs `docker-compose.yml:236` (`mem_limit: 2g`)
- **Problem:** V8 schedules its major GC against the 4 GB old-space ceiling — it tolerates the heap growing toward ~4 GB before doing an aggressive compacting GC. But RSS (heap + native bindings + socket buffers + `Buffer`s for media + V8 metadata) always exceeds heap, and the cgroup kills the process at 2–3 GB RSS. So under a real heap-pressure event (large broadcast fanout, media burst), the cgroup OOMKills the process while V8 still believes it has 1–2 GB of headroom it never gets to use.
- **Why dangerous:** This is the textbook "heap ceiling > cgroup limit" footgun. The web case is worse (4 GB heap vs 2 GB limit = 2x mismatch). An OOMKill (exit 137) of the api mid-BullMQ-job is exactly the cascade CLAUDE.md documents (lock released after 90 s, job re-executed → potential double Meta send), and `restart: unless-stopped` masks it as a transient blip instead of surfacing the misconfig.
- **Impact:** Under load the api/web get SIGKILL'd before GC can save them; on api this risks workflow job re-execution and drops all Socket.io connections; on web it kills RSC mid-render.
- **Fix:** Set the heap ceiling *below* the cgroup limit with headroom for native RSS — e.g. api `--max-old-space-size=2048` under `mem_limit: 3g`, web `--max-old-space-size=1536` under `mem_limit: 2g` (or raise `mem_limit` to ~5g if the 4 GB heap is genuinely needed and the VPS has room). NOTE: CLAUDE.md says the prod 4096 heap flag "must keep" (the broadcast runner + Socket.io fanout need that headroom), so lowering the heap as proposed directly cuts the headroom CLAUDE.md mandates — **raising `mem_limit` is the fix that respects both invariants**, not lowering the heap.
- **Confidence:** high
- **Locked-decision:** no
- **Verdict:** PARTIAL (downgraded HIGH→MEDIUM) — The numeric mismatch is real and confirmed: `apps/api/Dockerfile:73` and `apps/web/Dockerfile:205` both set `--max-old-space-size=4096`; `docker-compose.yml:236` (`mem_limit: 2g`) and `:430` (`mem_limit: 3g`). But the severity is overstated: the compose comments at `docker-compose.yml:232-235` ("2GB mem_limit is conservative because RSS exceeds heap … Bump if next start ever OOM-kills in steady state") and `:428-429` ("3GB tracks --max-old-space-size=4096 with margin") show this is a *deliberate, documented* posture with an operational backstop, not an oversight — and at 1-customer pilot load the heap won't approach 4 GB. The footgun is genuine (V8 won't aggressively GC before the cgroup kills it under a real burst) but it is latent, not active, and the suggested fix (lower the heap) conflicts with CLAUDE.md's "keep the prod heap flag" rule — corrected above to "raise mem_limit."
