# Website chat widget — developer guide

How to reason about, run, and test this channel. Product/architecture reference is
[webchatwidget.md](webchatwidget.md); the customer-facing install doc is
[webchat-install-guide.md](webchat-install-guide.md). This file is for *you*.

---

## 1. The one-paragraph mental model

A visitor's browser loads one static script from our own origin. That script builds
a chat UI inside a **shadow root** (so the host site's CSS and ours can't touch each
other) and opens an anonymous Socket.io connection to a **separate `/widget`
namespace**. It authenticates with a *public* site key plus an origin check — never
a cookie, so a visitor socket can never reach agent rooms. Inbound frames are
converted to a `NormalizedInboundMessage` and handed to **the same `ingestEvents`
every channel uses**, so from there on a website chat is just another conversation.
Outbound replies come back through the normal event bus, where a small delivery
subscriber pushes them to that visitor's socket.

The one thing that makes this channel different: **the visitor is anonymous and
ephemeral**. Their identity is a `vis_<uuid>` in their own browser's localStorage.
That single fact explains most of the design — why they're excluded from the contacts
directory, why they can't be broadcast to, and why history replay matters so much.

## 2. Where everything lives

### The client (one file, no build step in dev)

| Path | What it is |
|---|---|
| `apps/web/public/widget.js` | **The whole widget.** Hand-written classic script, ~2.3k lines, heavily commented. Source of truth; served as-is in dev. |
| `apps/web/public/widget.min.js` | Generated by `prebuild`, gitignored, served in **prod only** via a `next.config.ts` rewrite gated on `isProd && existsSync`. |
| `apps/web/scripts/build-widget.mjs` | esbuild minifier + a marker sanity gate. |
| `apps/web/public/webchat/socket.io.min.js` | Vendored UMD client, loaded lazily. |
| `apps/web/public/webchat/test.html` | Built-in sample page (`?key=wc_pk_…`). |

### The server

| Path | What it is |
|---|---|
| `apps/api/src/webchatwidget/webchatwidget.gateway.ts` | The `/widget` namespace: handshake auth, `visitor:message`, typing, receipts, history + pagination. |
| `.../webchatwidget-public.controller.ts` | Public HTTP: `GET /api/widget/config`, `POST /api/widget/media`, `GET /api/widget/media/:id`. |
| `.../origin-allow.ts` | The origin check. **Empty list = permissive, on purpose.** |
| `.../webchatwidget-delivery.service.ts` | Bus subscriber → pushes agent replies to the visitor socket. |
| `.../webchatwidget-frame.ts` | The sanitized shape a visitor is allowed to see (a strict subset of `Message`). |
| `apps/api/src/lib/providers/webchatwidget.ts` | The `MessagingProvider` impl. Sends are **no-ops** — delivery is realtime, not vendor I/O. |
| `apps/api/src/lib/providers/webchatwidget-config.ts` | Site-key resolution + TTL cache + trust-on-first-use recorder. |
| `apps/api/src/team/webchatwidget/` | Admin CRUD behind `@RequireRole("admin")`. |

### Where the channel touches shared code

These are the places a change ripples outward — check them when you change behavior:

- `packages/shared/src/providers/capabilities.ts` — `LIVE_CHANNELS`,
  `BROADCASTABLE_CHANNELS` (excludes widget), `EPHEMERAL_CONTACT_CHANNELS`,
  `ephemeralVisitorLabel`.
- `apps/api/src/lib/queries/contacts.ts` — `DIRECTORY_CONTACT_SQL` /
  `directoryContactWhere`, which keep anonymous visitors out of the directory.
- `apps/api/src/lib/media-storage.ts` — per-channel media policy, incl.
  `classifyWebpAsImage`.
- `apps/api/src/lib/identity/webchat-prechat.ts` — pre-chat identity, and the
  deliberate **no-auto-merge** block.

## 3. Running it locally

```bash
pnpm dev        # web :3000, api :4000
```

Then log in, go to **Settings → Website chat**, create a widget, and copy the key.

**The one gotcha that will bite you:** in dev the app and API are on *different
ports*, and `widget.js` defaults its API base to the script's own origin. Next's
rewrites proxy HTTP only — they do **not** carry a WebSocket upgrade. So a test page
must say so explicitly:

```html
<script src="http://localhost:3000/widget.js"
        data-webchat-key="wc_pk_..."
        data-webchat-api="http://localhost:4000" defer></script>
```

Serve that page over HTTP (Live Server, `python3 -m http.server`) — **never
`file://`**, which sends `Origin: null` and is refused.

Prefer `127.0.0.1` over `localhost` in URLs: Chrome resolves `localhost` to `::1`
first, and the API binds IPv4.

> ⚠️ **The dev API does not reliably hot-reload.** `node --watch` has been observed
> serving stale code — including silently dropping a message while still acking
> `{ok:true}`. If backend behaviour looks impossible, **restart `pnpm dev` before
> debugging further**, or A/B against a freshly spawned API:
> ```bash
> cd apps/api && API_PORT=4002 REDIS_URL="redis://localhost:6380/7" RUN_WORKER_INLINE=1 \
>   SWC_NODE_PROJECT=./tsconfig.json NODE_OPTIONS="--conditions=react-server" \
>   node --env-file=../../.env -r @swc-node/register ./src/main.ts
> ```

## 4. Testing

### The automated suite (start here)

```bash
pnpm dev                                            # in one terminal
E2E_BASE_URL=http://localhost:3000 pnpm test:e2e:webchat
```

23 tests, ~30s, real browser + real DB assertions. Covers the happy paths (visitor →
inbox → agent reply, media, refresh, close/reopen, workflows, outbound webhooks,
history pagination, both deploy modes) **and** a regression block for every bug that
has shipped and been fixed.

Run it **in isolation**, not as part of the full Playwright suite — the wider UI
suite is destructive on a shared dev DB.

Useful variants:

```bash
pnpm test:e2e:webchat -- --headed          # watch it drive the browser
pnpm test:e2e:webchat -- -g "webp"         # one test by name
pnpm exec playwright show-trace test-results/<dir>/trace.zip
```

### Before touching the minified path

`widget.min.js` is only regenerated by `prebuild`. To test it locally:

```bash
pnpm --filter @ccp/web exec node scripts/build-widget.mjs
```

The suite's last test skips itself if that artifact is missing.

### What to test by hand (things automation can't judge)

Visual/feel items, on a real phone if you can:
- iOS Safari with the keyboard open — the composer must stay above it.
- A long thread: scroll performance, and "Load earlier" anchoring.
- Dark mode, custom brand colours, a very long header title.
- Your own site's CSS — confirm nothing leaks in or out.

## 5. The invariants — break these and something real breaks

1. **A visitor socket is anonymous.** It authenticates with a public key + origin,
   never a cookie, and lives in its own namespace. It must never be able to address
   a team room or another visitor's conversation.
2. **Media is referenced by message id, never by URL on the wire.** The visitor
   frame carries `{kind, mimeType, …}` and the widget builds
   `/api/widget/media/:id?key=&v=` itself, so no signed URL leaks. Ownership is
   re-checked server-side on every fetch.
3. **`mediaKey` from a browser is untrusted.** The gateway requires the
   `media/{teamId}/` prefix — without it a visitor could name another tenant's blob.
4. **Anonymous visitors stay out of the directory.** Membership is *derived* (has a
   phone or email), never stored — so promotion can't drift.
5. **Pre-chat values are never a merge key**, in either direction. See
   `webchat-prechat.ts` and the exclusion in `findExistingCustomerIdByStrongKey`.
6. **The widget is a per-page singleton.** One bubble *or* one inline embed.
7. **Every send is idempotent** on `externalId = widgetId:visitorId:clientMsgId`,
   with a DB unique constraint behind it. Retries are safe by construction.

## 6. Debugging by symptom

| Symptom | Where to look |
|---|---|
| Widget doesn't appear | Browser console. `data-webchat-key missing` → the attribute. Otherwise check the script 404'd. |
| `connect_error: unknown_site_key` | Key wrong, widget deleted, or `isActive=false`. Note `resolveWebchatwidgetByPublicKey` is **TTL-cached** — a row edited directly in psql stays stale until it expires or the API restarts. |
| `connect_error: origin_not_allowed` | The page's host isn't in `allowedOrigins`. The API logs the actual origin. |
| Stuck "Reconnecting…" | In dev: almost always a missing `data-webchat-api`. In prod: check `connect-src` in the customer's CSP. |
| Message sends but never appears | Check the API log for `widget ingest failed`. **If the ack said ok and there's no row, suspect a stale dev API first.** |
| Inline embed invisible | Container has no height, or the selector never matched (console warns after 15s). |
| Upload fails with a bare "Upload failed." | Client/server MIME lists disagree — `widget.js` `OK_MIME` vs `mime-guard.ts`. Keep them in step. |

## 7. Deliberately not built (and why)

- **Per-visitor rate limits in Redis** — buckets are in-process today. Correct for
  one VPS; becomes N× looser the moment a second API instance exists. Same trigger
  as everything else in [operations.md](operations.md).
- **Cross-device identity** — a cleared browser is a new visitor. Intercom solves
  this with a signed logged-in identity; build it when a customer asks.
- **Retention sweeper for stale anonymous visitors** — nothing deletes Contacts or
  Conversations today, so widget rows grow without bound. Trigger: ~50k widget
  conversations on a tenant.
- **Reactions** — the frame has no reaction field; the inbox hides the control.
