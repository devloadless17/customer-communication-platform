# Pre-Deployment System Audit — WhatsApp Multi-Agent Shared Inbox (Next.js + NestJS, single-VPS pilot)

> Method: 14 staff-level domain auditors each read the real subsystem code (+ CLAUDE.md and
> the per-subsystem READMEs) and hunted bugs/races/risks; each was paired with an adversarial
> verifier that both rejected already-solved/false findings (16 rejected) and independently
> hunted for missed defects; a principal-architect pass merged the ~63 verified findings into
> this graded report. Every finding cites real `file:line` evidence traced in the source.

## Executive Summary

This is a genuinely mature codebase for a pre-pilot product. Across all 14 audited domains the hard, irreversible-consequence problems are solved correctly and verified against source — not doc theater. Message dedup is DB-enforced (`@@unique([teamId, channel, externalId])` with P2002 race guard), one-conversation-per-contact is structurally impossible to fragment (`@@unique([teamId, contactId])` upheld at every find-or-create site), the transactional outbox co-commits entity+event rows, the `OutboundSendAttempt` claim-before-send guard correctly distinguishes provably-not-sent from ambiguous on Meta failure, graceful-shutdown ordering is correct, and tenant isolation is enforced at the query layer on every cross-tenant path I traced. The verified scores cluster at 7–8.5/10, which is the right band for "production-ready for the stated pilot scale, with known sharp edges."

The single biggest risk theme is **at-most-once event delivery colliding with unbounded resume/retry windows on irreversible Meta sends**. Two findings sit on this axis and are the report's headline: (1) the 7-day `OutboundSendAttempt` retention sweeper GCs the *only* double-send guard for broadcasts that auto-resume after a >7-day pause — a duplicate **billed** template send to real customers (the lone CRITICAL); and (2) the outbox drainer dispatches outside the request's AsyncLocalStorage scope, pinning the `X-CCP-Depth` loop counter at 1 for every `message.sent` outbound webhook, defeating the loop guard and enabling an **unbounded** loop of irreversible Meta sends when a partner bounces the event back into `/v1`. Both are loss/duplication-of-customer-impact, not cosmetic.

Headline verdict: **NO — do not deploy today**, but the blocker list is short and surgical. One critical and a small set of high-severity issues (one duplicate-send path, one unbounded loop, one transient-failure-treated-as-permanent, one lost reopen event, one cross-tenant defense-in-depth gap) stand between this and a confident yes. None require architectural rework; all are bounded, well-localized fixes against code that is otherwise sound.

## 🔴 Critical Issues (MUST fix before production)

**1. 7-day `OutboundSendAttempt` retention GCs the only double-send guard for auto-resumed broadcasts — duplicate billed Meta template sends** *(BC-1)*
The per-recipient double-send guard (`claimBroadcastSendAttempt`, `broadcast-runner.ts:1407`) is the sole thing preventing a re-send on resume: the reconcile/abort branches only fire if the prior attempt row still *exists*. The retention sweeper deletes all attempt rows by `attemptStartedAt < cutoff` with no predicate on jobId prefix, `completedAt`, or `failedAt` (`outbound-send-attempt-retention.ts:82-86`). Broadcasts have **no** BullMQ layer, so the 7-day window justification (borrowed from `send-queue`'s `removeOnFail`) is false for `bc-recipient-*` rows; their resume path is the *unbounded-in-time* boot reconciler (`broadcast-runner.ts:1637`). The permanent-error breaker is explicitly designed to pause a broadcast on a dead/rotated credential until an operator reconnects — exactly the >7-day pause case, which is routine at scale.
**Impact:** every recipient of a long-paused broadcast that auto-resumes receives the template twice and the org is billed twice.
**Fix:** scope the retention DELETE so `bc-recipient-*` rows are only GC'd once their parent broadcast is terminal (`completed`/`failed`/`canceled`), OR keep them whenever neither `completedAt` nor `failedAt` is set. `msg-send-*` rows can keep the 7-day window.

## 🟠 High-Priority Issues (should fix before production)

**1. Outbox drainer dispatches outside ALS — `X-CCP-Depth` resets to 1 on every `message.sent` webhook, enabling an unbounded loop of irreversible Meta sends** *(EVT-1)*
`message.sent` is published via `publishInTx` and dispatched later by `OutboxDrainerService.tick()`, which runs in a bare `setTimeout` with no `als.run` (`outbox-drainer.service.ts:128`). The outbound-webhook subscriber reads `getChainDepth()` synchronously from ALS, which returns its default `0` (`correlation.ts:63`); `publishInTx` never captured chainDepth/correlationId, so the drainer cannot restore them. Every `message.sent` webhook POST therefore carries `X-CCP-Depth: 1`, always. A partner that bounces the event back into `/v1` to send another message never trips the `chainDepth >= 8` guard (`external-v1-messaging.service.ts:419`) — an unbounded loop of billed sends to a real customer. correlationId loss also breaks trace stitching. (The workflow `http_request` path is correctly bounded via `envelope._depth` — only the partner-webhook bounce is the gap.)
**Fix:** capture chainDepth + correlationId at publish time (inside `commitOutboundSend`, still in request scope), persist on the `OutboundEvent` row, and `als.run({requestId, chainDepth}, …)` around `bus.dispatchOutboxRow` in the drainer. Immediate backstop: a per-conversation outbound send-rate breaker.

**2. Transient DNS failure classified as permanent SSRF block — no retry, and it trips the auto-disable breaker on healthy webhooks** *(owh-4)*
`assertPublicHost` throws the same `SsrfBlockedError` for genuine SSRF *and* transient resolver failures (`safe-fetch.ts:316-321`). The worker treats every `SsrfBlockedError` as final: records the failure (bumping `consecutiveFailures`) and returns without throwing, so BullMQ never retries (`worker.ts:432-449`). A momentary resolver hiccup on a healthy public webhook URL permanently loses that delivery *and* pushes the integration toward the 20-delivery auto-disable. For an inbox product, dropped `message.received` deliveries mean a partner CRM silently misses customer messages.
**Fix:** give `SsrfBlockedError` a discriminating reason (`dns-failure` vs `blocked-range`/`bad-scheme`/`embedded-creds`); only treat genuinely-permanent reasons as `isFinal`, let `dns-failure` re-throw for normal BullMQ retry, and do not bump the breaker on it.

**3. Conversation reopen event lost when message tx2 fails after the closed→pending flip committed in tx1** *(INB-1)*
On a returning customer's reply-after-close, tx1 (the Serializable contact/conversation tx) commits the closed→pending flip and sets `reopened=true` (`ingest.ts:702-706`), but `conversation.status_changed` is published only inside the separate tx2 (`ingest.ts:937-960`). If tx2 hits a transient fault (P2024/P2034/DB blip — the exact load that triggers the 503→Meta-retry path), tx1 has already committed; on redelivery the dedupe pre-check passes, tx1 re-runs, sees `status='pending'`, so `reopened=false` and the event is permanently skipped. Two silent, load-correlated losses: the "On Conversation opened" workflow trigger + partner webhook never fire, and the `newConversation` list-splice never runs so the reopened thread stays invisible in teammates' Active view until reconnect. This is the exact split `ingest-call.ts:129-156` was rewritten to avoid.
**Fix:** mirror `ingest-call.ts` — only *detect* `needsReopen` in tx1; move the closed→pending CAS `updateMany` into tx2 and `publishInTx` the status-changed event (and build the splice row) only when `flip.count > 0`, so flip+event+row co-commit and are idempotent across retries.

**4. External `/v1` send path has a crash-window double-send; Idempotency-Key is optional** *(OUTBOUND-1)*
Unlike the inbox queue path, `/v1` send (text *and* the billed template branch) has no `OutboundSendAttempt` guard. Two triggers: (a) a crash between `binding.provider.sendText` returning and `completeIdempotency` leaves a pending row that's GC'd after TTL, and the partner's retry re-POSTs to Meta; (b) any partner omitting the optional `Idempotency-Key` (n8n routinely does — `external-v1-messaging.service.ts:437`) gets zero double-send protection, deduped only by `externalId` *after* Meta already charged and delivered twice. The stale-pending branch deletes the row and invites a fresh re-claim (`api-idempotency.service.ts:142-148`) with no `externalId`/`completedAt` recovery.
**Fix:** mirror the `OutboundSendAttempt` insert-before-Meta guard on the `/v1` text+template paths, keyed on the idempotency key or a server-generated stable id; on a stale-pending row, check for an existing Message before re-claiming and refuse-to-retry on ambiguity. At minimum make `Idempotency-Key` mandatory (400 when absent) on `/v1` send routes.

**5. Wire payload carries no schema/version marker — unversionable once partners parse it** *(owh-1)*
The outbound webhook body has no `version` field and no `X-CCP-Version` header (verified by zero grep hits across all three webhook dirs; header set at `worker.ts:403-421`). The codebase already shows the hazard (a prior epoch-seconds→ms timestamp fix, the flat-wire migration that silently broke `extractOriginApiKeyId`). Once thousands of orgs wire parsers, a v2 envelope cannot ship without silently breaking them. Near-free now, impossible to retrofit cleanly post-GA.
**Fix:** stamp `"v": 1` in the body (`subscriber.ts:284-291` and `service.ts` test payload) plus `X-CCP-Webhook-Version: 1` header now, and document the contract.

**6. Outbound-webhook enrichment reads are by-id with NO teamId scope — last structural barrier to a cross-tenant PII leak is absent** *(owh-5)*
Every enrichment query (message/contact/conversation/user) fetches by primary-key id only, no teamId filter (`outbound-webhooks.subscriber.ts:394-395, 426-427, 487-490, 579-582, 690-693`), while the team-row lookups in the same file *do* scope by teamId. No confirmed leak today (ids originate from team-scoped events), but zero defense-in-depth: any upstream bug carrying a foreign id would POST contact phone / message body / assignee email to the wrong team's receiver — high blast radius for a multi-tenant PII product.
**Fix:** add `teamId: event.teamId` to every enrichment where-clause; a cross-tenant id then silently drops the enrichment instead of leaking. One-line-per-query, do it before pilot.

**7. No outbox-drainer backlog/lag signal and no wedge watchdog** *(obs-1)*
The drainer is a single in-process timer with a single `inflight` boolean and no per-row timeout on `dispatchOutboxRow` (`event-bus.service.ts:56`). A subscriber that awaits something that never resolves (a hung partner webhook socket, a pool-starved write) pins `inflight=true` forever; every tick early-returns and `OutboundEvent` rows accumulate `publishedAt IS NULL` indefinitely. Realtime fanout, audit, analytics, workflow-dispatch and outbound-webhooks all ride this one drainer, so the entire event surface goes dark with green `/health`. MTTR is bounded only by a human noticing the product feels stale.
**Fix:** add a watchdog (track `tickStartedAt`; if inflight past ~60s, log fatal + force `inflight=false`), wrap each row dispatch in a timeout, and add an `outbox-lag` field to `HealthReport` (`SELECT count(*), MIN(createdAt) FROM "OutboundEvent" WHERE publishedAt IS NULL`) with a WARN past ~30s. This finding gates the verdict because it is the detection layer for the soft-wedge availability cliff a single-process pipeline carries.

**8. once-per-contact workflow ledger is never rolled back on run failure — failed run permanently locks the contact out** *(WF-1)*
For `triggerOncePerContact` workflows, the `WorkflowContactState` ledger row commits in the same tx as the run create, *before* execution (`dispatcher.ts:168-190`). If that run then fails for any reason (transient Meta outage on the first send, a config typo, retry exhaustion), no code path ever deletes the ledger row (grep confirms zero deletes; cascade is Workflow/Team-delete only). A once-per-contact onboarding/welcome flow that fails on its first execution marks that contact "already fired" forever, invisibly, across thousands of orgs.
**Fix:** on terminal failure of a ledgered run, best-effort delete the matching `WorkflowContactState(workflowId, contactId)` row so a re-trigger can re-fire; wire into `failRunFromRetryExhaustion` and the runner's permanent-failure branches. Keep the in-tx write (rollback-on-failure is safer than moving the ledger write post-terminal).

## ✅ Strengths (already production-grade — do not touch)

- **Message dedup** — `@@unique([teamId, channel, externalId])` with a cheap `findUnique` pre-check AND the P2002 catch as the real race guard, channel correctly on the Message row because dedup runs before any conversation link exists (`ingest.ts:527-537, 1024`).
- **One-conversation-per-contact** — DB-enforced via `@@unique([teamId, contactId])` and upheld at *every* find-or-create site (ingest Serializable retry, startConversation, broadcast, forward, `/v1`). Fragmented inboxes are structurally impossible. No Person/Customer super-entity exists (grep-verified).
- **Transactional outbox** — `publishInTx` co-commits the event row inside the entity tx; `claimBatch` marks `publishedAt` before dispatch via `UPDATE…RETURNING FOR UPDATE SKIP LOCKED` with per-team fairness; `dispatchedAt` brackets the success path as a queryable loss-window probe. At-most-once is honest and self-consistent.
- **`OutboundSendAttempt` double-send guard (inbox queue path)** — jobId-keyed insert before the Meta call, provably-not-sent (DELETE→re-send) vs ambiguous (KEEP+failedAt→refuse) classification, atomic Message-insert+completedAt stamp in one tx, 20s metaFetch timeout under the 90s lockDuration, non-idempotent POSTs never auto-retried. This is the highest-risk path and it is correct.
- **Inbound landing atomicity** — message insert + unreadCount increment + summary bump + `message.received` outbox row all commit in one `$transaction`, with monotonic `lastMessageAt` guards against out-of-order Meta redelivery and `{increment}`-from-DB (not snapshot+1).
- **Graceful shutdown** — manual SIGTERM handler does `server.close()` before `app.close()`, ~3s flush, `app.close()` capped at 90s under `stop_grace_period: 100s`; BullMQ `worker.close()` awaits in-flight jobs. Worker `lockDuration > step-timeout` asserted at boot.
- **Tenant isolation** — SessionGuard/ApiKeyGuard derive teamId server-side; service methods consistently use `findFirst({where:{id, teamId}})` gates before any read/write or irreversible send; `deleteMany`/`updateMany` carry `(id, teamId)` even after an ownership gate.
- **Crypto & webhook auth** — AES-256-GCM envelope (per-encrypt IV+tag, fail-loud in prod), SHA-256 API-key hashing with shape-gate-before-DB timing equalization, inbound Meta HMAC over exact raw bytes with `timingSafeEqual` + `phone_number_id` defense-in-depth.
- **SSRF defense** — DNS-resolve-then-pin against rebinding TOCTOU, per-hop redirect re-validation, notation-agnostic IPv6 block, credential-strip on redirect, response-body byte ceiling.
- **Realtime convergence** — re-auth on every recovered reconnect, three-tiered recovery (live / delta backfill / full refetch), markRead fires only when visible+on-thread, local `conversation:read` dispatch so the one-shot server CAS isn't a single point of failure, broadcast fanout scoped to the (empty) conversation room.
- **Workflow idempotency** — irreversible steps journal `in_progress` before the side effect; retry presumes-sent (`skipped_after_crash`) rather than double-firing; Redis per-run lock with heartbeat closes the BullMQ-locks-per-job gap; layered loop guards (DAG cycle detector, jumpsUsed cap, per-pickup ceiling, TRIGGER_DEPTH_MAX, X-CCP-Depth).

## 🚦 Deploy Verdict

**No — I would not personally deploy this to production for real paying customers today.** Not because the system is shaky — the foundations are genuinely strong — but because there is one verified path to duplicate *billed* Meta sends and one verified path to an *unbounded* loop of irreversible sends, both reaching real customers. Those two alone are disqualifying for a customer-communications product. The good news: the blocker list is short and every item is a bounded, well-localized fix against otherwise-sound code.

Fix these, in order, and the answer flips to yes:

1. **BC-1 — Broadcast retention double-send (CRITICAL).** Scope the `OutboundSendAttempt` retention DELETE to spare `bc-recipient-*` rows until the parent broadcast is terminal. ~0.5 day.
2. **EVT-1 — Outbox ALS depth-reset / unbounded loop (HIGH).** Persist chainDepth+correlationId on the `OutboundEvent` row at publish time and `als.run` around drainer dispatch; add a per-conversation outbound send-rate breaker as immediate backstop. ~1–1.5 days.
3. **owh-4 — Transient DNS treated as permanent SSRF block (HIGH).** Add a reason code to `SsrfBlockedError`; retry `dns-failure` and don't bump the breaker on it. ~0.5 day.
4. **INB-1 — Lost conversation reopen event (HIGH).** Move the closed→pending CAS flip + `status_changed` publish into tx2, co-committed, mirroring `ingest-call.ts`. ~0.5–1 day.
5. **OUTBOUND-1 — `/v1` crash-window double-send (HIGH).** Mirror the `OutboundSendAttempt` guard on `/v1` text+template; make `Idempotency-Key` mandatory on send routes. ~1–1.5 days.
6. **owh-5 — Enrichment teamId scope (HIGH, cheap).** Add `teamId: event.teamId` to every enrichment query. ~0.25 day.
7. **owh-1 — Wire payload version marker (HIGH, cheap, irreversible-if-skipped).** Stamp `"v":1` in body + version header before any partner integrates. ~0.25 day.
8. **obs-1 — Outbox drainer watchdog + lag health signal (HIGH).** Per-row dispatch timeout, inflight self-break, `outbox-lag` on `/health`. ~1 day. (Detection layer for the soft-wedge cliff; ship with an external uptime monitor on `/health`.)
9. **WF-1 — once-per-contact ledger rollback on failure (HIGH).** Best-effort delete the ledger row on terminal run failure. ~0.5 day.

Total: roughly **6–8 engineer-days** of focused work, no architectural rework. After that list lands, the medium-priority items are legitimate post-launch improvements — the multi-channel landmines stay dormant under the single-channel pilot, and the denorm/observability gaps are bounded by existing convergence mechanisms. At that point I would deploy this to the pilot with confidence.
